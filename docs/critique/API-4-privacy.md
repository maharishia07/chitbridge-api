# Critique · API-4 sweep: privacy (4 routes of routes/privacy.js, /api/privacy) · stage 2 · written before the first route edit

PERSONAL DATA: a storefront shopper's name, phone, e-mail, consent and privacy requests. Every value in this file, the tests and the PR is a made-up placeholder (zeros, nobody@example.test, "Test customer"); no real-looking phone, e-mail or name is anywhere.

(a) The brief assumes, checked against the code
- 4 routes, mounted at /api/privacy (server.js:476): TRUE. GET /facts :34 (public, listed at server.js:321), GET /me :58, POST /me/consent :66, POST /me/requests :79 (base lines). Main's register: all four "not started", 5, 5, 4 and 4 of 13 (the hardening columns foreign_id_404, idempotent_money_write, inbound_validated and trips_budgeted are already true or not applicable).
- ONE shared catch, `fail(res, e)` (:50-56), answers three ways: (1) code PRIVACY_NOT_MIGRATED -> 503 `{ code, error: 'Not migrated yet', message: e.message }`; (2) any error with a status BELOW 500 -> that status `{ code: e.code || 'REFUSED', error: e.message, message: e.message, [why] }`; (3) everything else, a carried 5xx included -> 500 `{ error: 'Failed', message: safeErr(e) }` (the generic sentence; the real error goes to the log with the request id). So unlike the identity routes a carried 5xx is NOT relayed here: it falls to the generic 500.
- Every throw that can reach branches (1) and (2), traced to its words (all FIXED, none carries exception, database or caller text): routes/privacy.js:43-46 403 NO_SHOP "This sign-in is not tied to a shop."; lib/privacy.js:84 503 PRIVACY_NOT_MIGRATED "Privacy records need migration b306|b307 — not run yet." (need(), :88-92); lib/privacy.js:246-248 400 (no code, so `REFUSED`) "Channel is phone, sms, whatsapp, email or chitbridge." / "Purpose is service or marketing." / "Say yes or no."; lib/privacy.js:430 400 "Kind is access, correct, erase, withdraw, nominate or grievance."; lib/privacy.js:442 400 "Which country’s law applies? ..." (a shop with no country). Unreachable from these routes because the route never passes the field: basis (:250-251), source (:252), who (:435, the fallback is 'the shopper'), country (:437) and received_at (:444-445). `e.why` is set only by privacy.refusal() (:221), which none of these four routes calls. A database error carries a SQLSTATE `code` and no `.status` (db/index.js sets none), so it can never take branch (2). Verdict: the relay RELAYS FIXED WORDS ONLY. NOT a finding. Once it sits in lib/privacy-contract.js the raw-error ratchet stops counting it, and the PR says so.
- No 200 carries exception text: TRUE. The facts, the shopper's answer and the two 201 bodies are built key by key from lib/privacy.js (facts :58, shopper :497, prefShape :99, reqShape :378). A scene makes the database throw a string with SQL in it and the scan covers 2xx, 4xx and 5xx bodies.
- No answer carries another shopper's data: the party and the shop come from the TOKEN only (whoOf :40-49; the body is read for channel, purpose, allowed and kind only). Every statement is parameterised with the token's two ids (shopper() :497-516, prefs :166, requests :398 with `party_id = $4`). The test sends a body that names another shop, party and identity and proves the database is handed only the token's ids and the answer holds none of the other's values.
- 9th world (S35): there is NO path id (S35 does not apply); the shopper comes from the customer token (middleware/customer-auth.js: identity_type 'customer' only; an owner or employee token is 401). The shop is the token's parent. No body or query key names a shop, customer or subject, so no foreign-id world can be played on a name; the proof is the hand case above (a body that names another shop's shopper changes nothing and returns nothing of theirs) and that a token with no shop is refused 403 NO_SHOP before any lookup. foreign_id_404 stays "not applicable" in the register.
- POST /me/consent and POST /me/requests are writes, not money writes (docs/contracts/api-hardening-scope.json lists none): idempotent_money_write does not apply. Each call appends a row (consent is append-only on purpose: a "no" or a withdrawal is a new row; a request is a new register entry), so a resend adds a second row; that is the designed behaviour and is frozen.
