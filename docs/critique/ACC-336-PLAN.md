## 1. The defect (main 4bba5eae)
- `lib/books-period.js:795` gstClose reads heads at span.end; `:826` refuseOverpay reads them at today. A challan's DATE decides what the set-off sees, not the period it pays.
- 336 (after the period): the set-off is right (utilised 4000, payable 6000) but the paid cash is never matched: output CGST ends a DEBIT of 4000 (K1 red: +4000, want 0).
- 336b (inside the period): the payment is already in the span.end balance, output reads 0, utilised 0, input credit stays "carried" (K2 red: utilised 0 payable 0 input 4000). K3b: a 6000 partial dated in the period reads payable 0.

## 2. The rule, and what is law, practice, convention (read before the copy is written)
- **Law, partly verified.** CGST Act s.49: deposits go to the electronic cash ledger, ITC to the electronic credit ledger; s.49(4): the credit ledger pays OUTPUT tax only (secondary summaries: cleartax.in/s/gst-input-tax-credit-utilisation, taxguru.in Rule 88A pages; the CBIC gazette PDF returned 404, so the section text itself was not read).
- **Practice.** A challan credits the cash ledger and is applied when GSTR-3B is filed, credit ledger first, cash for the balance; Table 6.1 shows "paid through ITC" and "paid in cash" (Tally help "Filing GSTR-3B and making payments", help.tallysolutions.com; learn.quicko.com, secondary). Credit-first is portal practice, not statute.
- **Convention (ours, R18): "a payment belongs to the period it NAMES".** A cash deposit is not tied to a period in law. Naming a period on the challan matches the portal's challan-to-return flow and is OUR internal rule; user copy says "paid for October", never "the law applies it to October".
- **Unverified or unmodelled, stated so nobody relies on them:** Rule 88A order text (not read; the order is the pack's, called through `posting.gstSetOff`, untouched here) · Rule 86B (cash floor) is NOT modelled: the K figures hold below its threshold only · s.50 interest can be paid from the same cash ledger, so the advance asset can be consumed by interest: label "paid in advance", never "refundable" · Zoho Books not reached.
- **The rule:** the period's set-off is credit first over what the period owes BEFORE its own payments; payments match a period by the period they name, never by date; cash above the net due is an advance asset, never input credit.

## 4. The change: one calculation widened, never a second formula
Seams (`node seams.cjs gstClose`, `settledAsOf`): one close `gstClose`, one balance reader `gstBalances`, one engine set-off `posting.gstSetOff`. Nothing is added beside them except the surplus event (4.4).
1. **Reader.** `gstBalances(handle, entity, asOf, preRead, pack, { paidFor })` gains ONE option. The add-back is **signed and made on the head's NET, BEFORE the clamp at `books-period.js:524`** (`outputNet < 0 ? -outputNet : 0`): `outputNet' = outputNet - namedPaymentsDatedUpToSpanEnd`. Adding after the clamp loses a payment larger than the span.end credit (T11). Callers without the option (`gstPayableAt`, `refuseOverpay`) are unchanged.
2. **The carrier.** `gstPay` writes `tax_period = span.key` (b849, `schema.hasColumn` guard, never in source_ref). Payments for a period = unreversed debits on the head's output/rcm role whose `tax_period` = span.key (books-store.js:215 reversal shape). No carrier (legacy): counted only by the single-candidate rule, else `paid_note`; the close still posts (T8b).
3. **The close.** Base output (4.1) → `setOffOf` → utilised, owed-before-payments. `paid` = all named payments (those dated up to span.end come in through the add-back; those dated after are not in the balance). `still = max(0, owed - paid)`, `excess = max(0, paid - owed)`.
4. **The surplus posting path (engines event; today there is none: posting.js has only the role rows, reg-in.js:339 and :1085).** New engines rule **`tax_advance`** in `src/posting.js`, beside `tax_setoff`/`tax_payment`: input `{ heads: { cgst: 40 ... } }` (major units, like tax_payment). Rows per head with an amount: **Dr `pack.taxLedgers[head].advance` (asset) · Cr `pack.taxLedgers[head].output`**, equal amounts, balanced by construction. Voucher type Journal (the same table as tax_setoff, posting.js:1611). **Neutrality:** the rule reads only the pack's `taxLedgers[head].advance` and names no country. A pack without the key throws the pack's own words (`messages.noAdvanceRole`, a new text key with a neutral fallback); the api then posts no surplus and answers the keys + `paid_note`: AU and AE today. IN has the role since engines v1.85.0 (b850 chart rows). AU/AE keys and wording come from cb-country in their own PRs (AU "credit on your activity statement account; the ATO may offset it or refund it on request"; AE "payment made in excess, held as credit in your FTA account"; both TO CONFIRM against primary pages). It posts dated today(shop); today not open fails the whole close in words.
   **Landing order (api CI tests against engines):** (i) engines PR: the `tax_advance` rule + `messages.noAdvanceRole` + tests + CHANGELOG; the tag is cb-release's, next above the HIGHEST existing tag (fetch tags first), Athi's yes; (ii) the api build PR carries the `engines.lock.json` pin bump and `tools/adopt.cjs` output IN THE SAME PR (an engines change that moves an api answer lands WITH its api adopt; a web-first adopt reds engines-pins and needs Athi's --skip-main-ci); (iii) the web twin (section 8) after. 5. **Replay = option A, mismatch not recompute.** The first close writes the figures it used on its own entry: `journal_entry.tax_close jsonb` (**b854**, `migrations/b854_journal_entry_tax_close.sql`, Athi runs it after b849; carried: base, utilised, payable, paid, excess, the paid entry ids, currency). A replay (`seen`) reads that column and answers it exactly as stored, `duplicate:true`, same entry_no; it never calls `setOffOf` or `gstBalances` on today's ledger. It then compares two CARRIED totals: the stored `paid_entries` against the live payments named for the period, **ordered by `created_at`, then `entry_id` (never entry_no, never posting_date)**. A payment created after the close entry is reported as `paid_since_close_minor`; a stored payment now reversed, or any difference that is not a later-created payment or a reversal, answers `paid_note` and raises a service ticket (mismatch ticket) instead of silently re-solving (T5b). A close that utilised nothing and had no excess writes NO entry (posting refuses an empty set-off): its replay answers `nothing_to_set_off` plus the live still-owed from `gstPayableAt`; nothing stored, nothing to compare. A column absent (b854 not run) or NULL (a close made before it, T19): answer duplicate + `paid_note` "closed before the figures were carried", write nothing, **never backfill**.
6. **One meaning per name.** Close answer: new `owed_before_payments_minor` (per head) and `owed_before_payments_total_minor` = the period's own set-off; `payable_minor`/`pay_total_minor` stay with the same values as aliases for old readers, marked "do not ask for money from these" in the dictionary. New `still_to_pay_minor` and `still_to_pay_total_minor` = after the payments named for the period (what a pay form may ask for); `paid_before_close_minor`, `excess_paid_minor`, `paid_note`, `paid_since_close_minor`. The F3 reader keeps its function `gstPayableAt` and its key, relabelled in its docblock and the dictionary "STILL OWED after payments (cash forecast)", so one word never carries both meanings in the same docs (test NAMES).
7. **gst-returns.js:1117 `settle_` does NOT use `gstBalances`** (correcting rev 1): it runs `posting.gstSetOff` on the return sheet's invoice-derived payable and ITC, a second INPUT to the same engine function, not a second formula. It stays. The build adds one comparison: the return's 6.1 cash column against the close's carried `payable`/`paid` for the same period, a difference raising a mismatch ticket (two carried totals compared). **books-todo.js:175 (rev 3, critic MUSTs):** it moves to the close's own figure, with no date rule left. A CLOSED month answers the stored `still_to_pay` MINUS the payments named for it that were created after the close entry (`paid_since_close`, carried-total arithmetic: `carriedClose`), on the replay answer and on the Todo, so close (still 6000) then pay 6000 owes 0 (test R1). An UNCLOSED month uses `closeFigures` (the close's own calculation: named payments, credit first), never `gstPayableAt` at the month end and never a date, so a challan paid on the 9th/18th for last month counts (test R2). Where the payments cannot be read (carrier columns not applied, a payment with no period) the old read stands. Both go through the one function `gstStillOwed`.

**4.8 The surplus is dated max(span.end, latest named payment date)** (SHOULD, done; test R3): a 20 Oct payment gives a 31 Oct surplus, so the 31 Oct ledger shows output 0 and advance 4000; a 9 Nov payment gives a 9 Nov surplus. The set-off stays dated span.end.
