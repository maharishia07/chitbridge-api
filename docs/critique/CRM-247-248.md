## Privacy requests stay allowed on a deleted party (legal)
Hiding is not erasing: the shop still holds the person's data, so an access or erasure request about them must be loggable and its due date must run (DPDP s.11-13, Privacy Act APP 12/13, GDPR art. 15/17 — cite-check before external use). Refusing it would hide a statutory clock. Built: POST /privacy-requests with a deleted party_id = 201.

## DECISION PACK: a deleted party's phone or name imported again — restore or new?
Built (clear): never merge into a deleted party. Phone match -> the row is ADDED as a new party (new id, no old history). Name match -> mint() is find-or-mint on the name (unique index), so a new party cannot take the deleted one's name; the row is SKIPPED with "Same name as a deleted party", the deleted party untouched.
Options for the name case and for walk-in/manual add on the same name: A new party under a numbered name (needs a mint rule change, owner: local-identity). B RESTORE: unhide the old party with its history (needs a new owner-only restore route + sentence; none exists today). C ask per row (preview says "restore or add new"). Common practice, recalled and NOT fetched: Shopify customers with orders cannot be deleted and a re-add is a new customer; HubSpot keeps deleted contacts restorable for a period and a re-import creates a new record; Zoho moves deleted records to a recycle bin and offers restore. Recommendation: B for the name collision (history is what the shop wants back) plus A for phone-only, owner to confirm.
