# Critique · API-4 sweep: simulator (3 public routes: routes/simulator.js, /api/simulator) · stage 2 · written before the first route edit

(a) The brief assumes, checked against the code
- 3 routes, 1 router, all signed out (no `auth`, no token check anywhere): GET /content (base :38), POST /lead (:63), POST /feedback (:88). Main's register: all "not started"; the 7 core columns false on all three; strict_input fails on both POSTs; output_allowlist and trips_budgeted fail on all three (round-trips.budget.json holds no simulator line; tools/round-trips.budget.json measures 6, 1 and 1). foreign_id_404, idempotent_money_write and inbound_validated do not apply (no id in any path; none is in api-hardening-scope.json `money_writes`, `inbound` or `public_ids`; they are a visitor's own public writes, not a peer or webhook door). Money: none. The 9th world has no meaning: signed out, so there is no "another shop"; the id surface is the body's `leadId`.
- Limit (server.js:302-318): `/api/simulator` sits under `publicLimiter`, 240 requests per minute, keyed by lib/limiter-key.js `callerKey`: `ip:<address>` for anyone without a verifiable ChitBridge token (trust proxy is 1), so it is per IP. 240 lead rows (and 240 e-mails to the leads inbox) a minute from one address is generous for a form; a finding, not changed. The limiter's own 429 is express-rate-limit's, not a Problem: listed under x-simulator-refusals.
- Relays traced. GET /content answers `message: safeErr(err)` on a 500; safeErr (lib/respond.js:13) logs the real error and returns the ONE constant 'Something went wrong — please try again.', so it can pass nothing of the database error. The other two 500s are the literal 'Could not record that — please try again.' (no relay). No sentence in the file interpolates anything into an answer. notify() never answers the caller. The 200 bodies carry no exception text: /content the rows of six `SELECT *` (so a column added to a sim_* table is published at once: output_allowlist cannot pass honestly, SQL frozen), /lead `{ token, leadId }`, /feedback `{ ok: true }`.
- FOREIGN-KEY ORACLE (SEC-100). sim_feedback.lead_id REFERENCES sim_leads(id) (migrations/000_baseline_2026-10-21.sql:9028), no RLS on either table. POST /feedback sends any 36-character [0-9a-f-] `leadId` to the INSERT: a real lead id answers 200 and writes the row; a well-formed unknown uuid fails the key (23503) and the catch answers the generic 500; a 36-character non-uuid ('------------------------------------') fails the cast (22P02) and answers the same 500. So 200 against 500 tells a signed-out caller whether a uuid is a lead. Uuids are random (gen_random_uuid, 122 bits) and never listed, so it needs a candidate id first: rate LOW. An array `leadId` (`["<36 chars>"]`) passes the regex (the array prints as its one element) and reaches pg as an array: 22P02, 500. Proved in the test over a stand-in that models the key; listed for cb-security with file:line, not fixed.
- Other edges (reported, not changed): `rating` takes any finite number (`+req.body.rating`), but the column is integer: 3.5 and 1e21 are 22P02, 5000000000 is 22003, all the generic 500; `[5]`, `true`, `"7"`, `null`(0) are taken. `email` only has to contain '@' ('@' passes); no length cap on name, email, org, message or section beyond the 256 kb body limit. A request with no JSON body reaches the handler as `{}` in this stack (body-parser) and is the handler's own 400; only an app with no parser (`req.body` undefined) throws a TypeError, caught: the generic 500. SIM_SECRET falls back to the published literal 'sim-lead-dev-only' when neither SIM_JWT_SECRET nor JWT_SECRET is set (server.js has a boot check for JWT_SECRET; the fallback only matters if both are absent), and the token it signs is checked by no route at all, so the "gate" is cosmetic: GET /content stays public whatever the visitor holds (cb-security / cb-demo). `name` reaches the e-mail SUBJECT unescaped (`New tour lead: ${name}`), and so does `section` in the feedback subject: esc() is applied only to the HTML body. `.trim()` leaves an inner CR/LF in a name; the sender is Resend's HTTP API (a JSON field, not a raw header), so header injection is the provider's to refuse: a FINDING for cb-security, not fixed.

(b) Conflicts with rules
- NO BEHAVIOUR CHANGE. The body schemas say what the handlers already take: an object or a list (a list reads as no fields), nothing required (the handler's own 400 names name and e-mail), every value anything (String(...) of whatever came). An unknown key is dropped today, so strict_input STAYS OPEN on both POSTs (closing it turns a dropped key into a refusal). The schema check can refuse nothing; the refusal the kit declares for it is declared at 400, the status the route answers itself. error_tests: GET /content is tested at 500 (its only declared refusal); the POSTs at 400 and 500.
- The relay of GET /content moves into faultOf and still relays only the constant sentence; the raw-error ratchet stops counting it (the PR says so). The two literal 500s keep their bytes.
- output_allowlist and trips_budgeted are LISTED (laptop1 ruling 24 Oct), not closed or budgeted by hand.

No caller in chitbridge-web or the web worktree reads /api/simulator (the /tour page that does lives outside those checkouts), and docs/contracts/web-api.json holds no entry, so no web twin is needed; the page reads by status and `token`, `leadId`, `ok`.
