# Critique · API-4 sweep: capture (12 routes of routes/capture.js) · written before the first route edit

(a) The brief assumes, checked against the code
- 12 routes, mounted at /api/capture (server.js:453): TRUE. The register counts 12 rows of routes/capture.js, all "not started".
- Three of them are an OUTSIDE CONTRACT (Meta / the e-mail provider): GET /webhook/whatsapp (the verify handshake: echoes `hub.challenge` as `text/html`, a bare 403 `forbidden` otherwise), POST /webhook/whatsapp (200 even when handling fails; 401 `{ error: 'bad signature' }` for an unsigned body) and POST /webhook/email (the same). server.js:239 claims their raw body before express.json; the HMAC (`hmacOk`) is over those raw bytes. Nothing in the repo shows a real provider ever read a refusal body (the file says "NOT YET EXERCISED AGAINST A REAL PROVIDER"), so the safe reading wins: the three webhooks are NOT edited at all, not even their 401/403 (their statuses, bodies and content types are byte for byte today's). They stay partial on error_shape, codes_registered, schema_in and error_tests, and the sweep adds the proof instead: the test replays 20-odd signed and unsigned deliveries through the real route over a stand-in db and fails on one changed byte.
- Nine routes are the authenticated intake (POST /simulate, GET /pending, POST /:id/structure, /:id/raise, /:id/convert, /:id/dismiss, GET /consolidate, GET /stores, POST /stores). Every one answers `{ error: '<label> failed', message }` from a catch; none writes a refusal of its own: TRUE.
- RELAYED TEXT (round-1 rule 1), traced to every throw. The relays are `err.message` when `err.status` is set: simulate, convert, dismiss, POST /stores (any status), structure and raise (status under 500); the other catches use safeErr. The throws that can carry a status: lib/capture.js (raw_text required 400 · Capture not migrated yet (b104) 503 · Capture not found 404 · Capture not found or already handled 404 · That message has already been handled 409 · Read the message first 409 · Nothing was read out of that message 409 · The reader returned nothing usable 422), lib/stores.js (phone required 400 · Stores are not migrated 503) and, through structure only, lib/ai.js invokeSkill (401 · 400 unknown skill/images · 413 · 422 truncated/unparseable · 402 budget · 429 rate · 503 not connected/paused/metering; and 502 `AI HTTP <status>: <provider body>`). All but the 502 are fixed sentences in our code. The 502 carries up to 240 characters of the provider's own body, but structure relays only under 500, so it answers the constant safe sentence (status kept 502, as today). pg errors carry a code, never a status (db/index.js sets none), so a database text cannot ride on a status. Conclusion: no database, provider or model text can reach an answer. FINDINGS for cb-security, not fixed (no behaviour change): the 422 sentence tells a shopkeeper to "raise AI_MAX_TOKENS" and the 503 `AI not connected — set ANTHROPIC_API_KEY.` is operator wording, but the latter is a 503 and structure never relays it; the former does reach the shop. Because each relay is a fixed sentence the routes can still reach 7/7, but moving the relay into a contract function (`faultOf`) is a relay in a spec: the raw-error ratchet stops counting it; the signer reads the spec.
- Statuses written by the handlers are `err.status || 500`, so a thrown 502/503 keeps its status with the safe sentence: the contract function keeps that (a spec with the thrown status), it does not squash it to 500.
- GET /consolidate always answers 500 on a fault (never the thrown status): kept.
- The web calls five routes (intake.html, cap-intake.js, the app.html EP table): objects or no body, never a list; no repeated query. docs/contracts/web-api.json holds no capture entry.
