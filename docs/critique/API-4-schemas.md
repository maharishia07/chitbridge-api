(a) The brief assumes, checked against the code
- 7 routes, mounted at /api/schemas (server.js:408): TRUE. GET /my :25, POST /create-default :44, GET /fields :86, DELETE /fields/:field_key :184, PATCH /fields/order :255, PATCH /fields/:field_key :314, PATCH /visibility :427 (base lines). Main's register showed all seven "not started".
- Three express-validator chains answer `{ error: 'Validation failed', details }` through validate() at 400: PATCH /fields/order (`order` a non-empty list), PATCH /fields/:field_key (six optional keys) and PATCH /visibility (one of three words). Measured on the base: a null `field_name` is listed TWICE (not text, and empty as text), a list given as a value is checked element by element (so `{ visibility: ['public'] }` passes the chain and then fails in the database as a 500), and `required` accepts the words true/false and the digits 1/0.
- Every other refusal is a bare `res.status(N).json({ error, message })` with fixed sentences; the 409s already carry `code` (LOCKED · REQUIRED · IN_USE · MIGRATION) and the in-use ones `used_by`. Every 5xx goes through safeErr (`message` is the generic sentence): TRUE for six routes.
- **POST /create-default sends the bootstrap's own error text in its 500** (base :49 `message: r.error || 'no schema'`; lib/schema-bootstrap.js:114 returns `{ created: false, error: e.message }`). A failing database answers 500 with a database sentence in `message` (measured: `relation "..." does not exist -- SELECT ...`). TRUE, and not caused by the sweep. FINDING for cb-catalogue and cb-security, NOT fixed here (behaviour is the owner's); the sweep keeps the answer byte for byte, words it as a Problem (detail and hint say nothing of the cause), freezes it, and shows the exact text in a test so it cannot grow. The route stays unsigned until the owner closes it.
- No 200 carries exception text: TRUE (the body scan runs a database that throws SQL text and a bootstrap that throws, over all 126 recorded answers). lib/column-rules.js and lib/catalogue-columns.js words are fixed sentences.
- All seven are entity-scoped from the token; the two column-key routes (DELETE and PATCH /fields/:field_key) read `WHERE es.entity_id = $1 ... AND sf.field_key = $2`, so another shop's key is "no row" => the same 404 as an unknown key. Run as the 9th world offline (tests/lib/foreign-id-world.cjs) and written as a T2 case (tests/schemas-truth.realstack.cjs, written, not run here: the local stack was down).
- Callers (grep of chitbridge-web/public, the demo scripts and the api tests): the web sends `{ field_type }`, `{ unit }`, `{ required }`, `{ field_name }` to PATCH /fields/:key and `{ order }` to PATCH /fields/order (cap-catsetup.js:1590, 1626, 1644, 1655, 1705, 1890); GET /fields and DELETE /fields/:key send no body (cap-catalogue.js:154, cap-catsetup.js:1857, 1921). GET /my, POST /create-default and PATCH /visibility have no web caller; the demo and proof scripts send no body, `{}` or `{ visibility: 'public' }`. No caller sends an array body or an unknown key.
