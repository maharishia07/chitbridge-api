PERSONAL DATA: a person's phone, e-mail, PAN, voter ID, driving licence and Aadhaar. Every value in this file, the tests and the PR is a made-up placeholder (0000 0000 0000, AAAAA0000A, 0000000000); no real-looking number is anywhere.

(a) The brief assumes, checked against the code
- 4 routes, mounted at /api/identity (server.js:410): TRUE. GET /documents :127, PUT /documents/:scheme :221, POST /documents/:scheme/code :389, POST /documents/:scheme/verify :405 (base lines). Main's register: all four "not started"; foreign_id_404, idempotent_money_write and inbound_validated already true or not applicable.
- Four handlers answer `message: e.status ? e.message : safeErr(e)` under `e.status || 500` (:170, :337, :402, :418): TRUE. Any status relays the error's own words, a 5xx included. Every throw that can reach them: resolveSubject (:199-214) throws 403 IDOC_SUBJECT_FORBIDDEN with two FIXED sentences; vaultcrypto.encryptVault (lib/vaultcrypto.js:41-45) throws a 503 VAULT_ENC_UNCONFIGURED with one FIXED sentence, unreachable because the PUT checks isConfigured() first (:259). The sender (lib/notify.js) is called inside a try in lib/iddoc-verify.js:62-67, which logs and carries on, so it never reaches the handler; schema.hasTable catches (lib/schema.js:93-95); db/index.js raises plain Errors and pg errors, none carries `.status`. So no exception, database or provider words ride the message relay today. NOT a finding for the message. The relay still relays: once it sits in lib/identity-docs-contract.js the raw-error ratchet stops counting it, and the PR says so. A thrown 5xx that carries a status would relay its message; none exists today (replayed with an injected 502 and 503).
- FINDING for cb-security (not fixed, frozen): the same catch answers `error: e.code || 'Server error'`. A database or network error carries a `code` of its own (a SQLSTATE such as 42501, or ECONNRESET), so a 500 puts that code in the `error` key (routes/identity-docs.js:170, :337, :402, :418). It is five characters of database vocabulary, never a sentence, never a value; it is replayed and kept as it was. The route is never 13 of 13 while it does.
- No 200 carries exception text: TRUE. Documents answer the mask and the verdict only (:145, :152); the PUT answers scheme, mask, status, filer (:326, :331); code and verify answer lib/iddoc-verify.js bodies (iddoc-verify.js:87, :114). A scene makes the database throw a string with SQL in it and the scan covers 2xx, 4xx and 5xx bodies.
- A full document number is never echoed: TRUE. GET selects value_masked, never value_enc, value_hash or verification_ref (:145); PUT returns value_masked (:326); POST /code answers `sent_to`, masked (iddoc-verify.js:33, :87). Aadhaar is never stored: store:false, the value never reaches the database (:106, :258); only XXXX XXXX + last four. The test posts a made-up PAN, voter ID, licence, Aadhaar, phone and e-mail and fails if any answer holds the full value.
- ONE 200 can carry a code: `dev_otp` in POST /code, only when devOtp.mayExposeOtp() (armed, not sealed, a local stack, opted in: lib/dev-otp.js:137). Local stack only, frozen, listed for cb-security.
- 9th world (S35): `:scheme` is a scheme NAME, not another person's id; the person always comes from the token (auth.entityOf, req.identity). But a body or query CAN name another identity: `identity_id` (PUT body :273; code and verify body or query :348; GET query :135). resolveSubject answers 403 for a stranger, a foreign shop's actor, an unknown id and a non-actor with the SAME words, after one lookup (:205): nothing is revealed, the record is never returned, foreign = unknown byte for byte. It is a lookup-then-403, not 404: an owner question (cb-security), not changed. The foreign-id world runs on POST /code and /verify (another shop's row answers as no row: 404 IDOC_NOT_FOUND), and a hand case on identity_id.
- POST /code sends an SMS or e-mail (lib/notify.js). Not a money write in the register's sense (docs/contracts/api-hardening-scope.json money_writes lists none of these; nothing is written to a ledger or a usage table; the sender is not metered here). It resets the wrong-attempt counter on every call (iddoc-verify.js:86 packs the count at 0) and has no limit of its own: listed for cb-security (message cost, code re-issue), kept. idempotent_money_write does not apply.
