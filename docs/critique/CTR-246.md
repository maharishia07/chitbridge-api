# CTR-246 critique - a bridge-less bill from a bridge-always till build is refused (CTR-212 S5), written before the code, 13 Nov 2026
Source: PM/BUILD-PHASE-2026-11/04-counter.md section 5 (S5), PM/CTR-212-PLAN-2026-11-08.md section 6 + R6/R10, ATHI-DECISIONS 8 Nov (CTR-211 open item: "removing the WHOLE bridge still skips the check"). Read against api origin/main c32056f2.
(a) What exists, checked in code
- `lib/send-money.js pairMismatchOf` returns null when `invoice._cb.bridge` is absent (line 323 area): that is the gap. A till bill with an invoice and no bridge sails through.
- The bill carries NO build stamp today. `TILL_BUILD` (till.html, `var TILL_BUILD`) is only read by pageStale and the diagnostics `device.page`. `business_json.page` on a copy is the mint PAGE stamp (a different thing: which app page minted the chit). So the stamp must be added to the bill; nothing carries it now (`seams.cjs TILL_BUILD`: nothing).
- Two builders make the chit body: till.html `chitOf` (browser + phone) and tools/tally-connector/till.js (shop PC program, `business_json.till = {id,name,host,by}`). Both take a bill the page finished; the agent does `Object.assign({...}, b)` so a key on the bill survives. Both get the stamp (existing duplication, not widened).
(b) Design
1. STAMP: till.html finish() sets `bill.till_build = TILL_BUILD` once, with the invoice (never at chitOf time: a bill finished by an older build and rebuilt/queued by a newer page must keep the OLD build, or an old bill with no bridge would be refused and lost - "a bill can never be lost", TILL-41). chitOf and till.js put it at `business_json.till.build` (beside `id/name/device_id`, which already ride `till`; `holder.tillClaimOf` merges only `by/device_id` so `build` survives). TILL_BUILD is bumped (every change to the page does).
2. RULE (server, lib/send-money.js `bridgeMissingOf(invoice, till)`, pure, no arithmetic): invoice is an object AND has no `_cb.bridge` AND `till.build` is a readable stamp (`YYYY-MM-DD.tag`) => `{ build }`. A build is "bridge-always" exactly when it carries the stamp, because the stamp ships in the same build that always sends the bridge (engine tax >= 1.74.0 is on the page). No calendar floor (the CTR-214 lesson: the bill's own stamp decides). No stamp / unreadable stamp (old build) => COUNTED + logged `send.bridge_absent`, passes as before (same pattern as headsAbsentOf).
3. REFUSAL (routes/chits.js sendBridge, before pairMismatchOf; drafts exempt like the pair check): 409 problem+json, code `BRIDGE_MISSING` (own code, R6: not MONEY_UNBALANCED; the till's `step`/`pair` readers must not mistake it). NO override (a fault, not a judgement; same as CTR-211 pairs). Shopkeeper words, three beats: "This bill arrived without its tax check figures, so it was not saved. Reload the counter and make the bill again. We have been told." Keys: `build`, `words`. ONE ticket via `money-check.raiseMissingBridge`, which calls the SAME `fileTicket` as `raisePair` (R6); the two are mutually exclusive on a bill (the pair check needs a bridge, this one needs none), so a bill cannot raise two. Ticket key = sha1(shop|bill|'bridge'|build): a retry under a new client_ref is the same bill.
4. REGISTER (cb-api): `docs/ERROR-CODES.md` row + `docs/error-codes.json` (generated), FIELDS.md rows for `business_json.till.build` and the 409, `lib/till-contract.js` note (409 now has THREE shapes), RFC 9457 through the one `problem()` + `said()` path (`res.locals.code` set), trips unchanged (no query added; the ticket path is the existing one).
5. TILL (twin): till.html treats `_code === 'BRIDGE_MISSING'` like MONEY_UNBALANCED for the red stoprow (line ~24727). Web gets the vendored copy (`scripts/vendor-till.cjs`, CB_WEB_DIR at the web worktree). The web answer moves (till.html bytes), so twin PRs, same branch name, web first.
(c) Simpler way considered: refuse every invoice without a bridge. Rejected: old builds and frozen invoices (pre v1.74.0) would be refused and bills lost. Server rebuild of the bridge: rejected (second calculation; engines keeps bridgeOf_ private, CTR-211 ledger).
(d) Risks and answers
- Forgery: a client can drop the stamp too. Accepted and said: this is a guard against a till regression (a build that stops sending the bridge), not against a hostile client, who can forge the whole bill. Not claimed otherwise.
- Queued bill refused offline: the existing 409 handling holds the row with words (`q._why`); the refusal is for a build that is itself faulty, and the owner sees it red. Same as CTR-211 pairs.
- send-money.js is shared with counter U6 (engines tag v1.83.0, per-head compare): this adds ONE function and one call; no edit to pairMismatchOf/headsAbsentOf. U6 rebases on it; pairMismatchOf's complexity ratchet is not touched.
- The stamp is a free string from the till: only its SHAPE is read, never parsed for order.
