# Critique · API-4 sweep: attachments (2 routes: routes/attachments.js, /api/attachments) · stage 2 · written before the first route edit

(a) The brief assumes, checked against the code
- 2 routes, 1 router: POST / (base :32) and GET /:id (base :78). Main's register: both "not started"; every core column false on both; POST fails strict_input and output_allowlist; GET fails trips_budgeted (round-trips.budget.json:176 reads 0, the placeholder). inbound_validated and idempotent_money_write do not apply to either (neither is in docs/contracts/api-hardening-scope.json `inbound` or `money_writes`; an upload is the caller's own data on its own session, not a peer or webhook door). Money: none.
- Every text that can reach an answer, traced: both catches answer `message: safeErr(err)` (lib/respond.js:13), which logs the real error and returns the ONE constant 'Something went wrong — please try again.'; it can pass nothing of the error (pg text, object-store provider text from lib/storage-object.js, a header error are all dropped). Every other sentence in the file is a literal; nothing is interpolated. 200 bodies: POST `{ id, name, mime, size }`, where `name` and `mime` are echoed AS SENT (not the sliced values stored, and not coerced: `name: {}` or `mime: 7` comes back as it went); GET the stored bytes. Both are the caller's own text to the caller (a self-echo, no one else's data), so it does not matter for output_allowlist, and it is not changed. Neither route puts exception text in any answer.
- Foreign keys and ids (SEC-100). migrations/000_baseline_2026-10-21.sql:2184 `cb_attachment` has NO foreign key at all (chit_id, message_id, uploaded_by are plain uuid), FORCE RLS `rls_entity` on entity_id (:9811); `chit_messages` has RLS on entity_id (:9847) and PK (message_id, entity_id). So: no existence oracle by foreign key. chit_id is looked up `WHERE chit_id=$1 AND entity_id=$2` under withEntity, then 403: a foreign chit and an unknown chit both find no row and answer the same 403 (door-gated after a scoped lookup = uniform; proved byte for byte in the test). message_id is looked up under RLS only (caller's own copies), a foreign or unknown id finds nothing, `vis` is undefined and the file fans out to the whole roster carrying that message_id: it answers 200 exactly as a made-up id would (no oracle), but the row IS written with a message_id the caller never proved it can see. line_index is `parseInt` of anything: `'abc'`, `''`, `true` give NaN, which Postgres refuses (22P02, integer) inside the first INSERT, so the answer is the safe 500 and nothing is written; `'3abc'` stores 3; `1.9` stores 1; `1e10` is out of range for integer (500).
- Findings (listed for cb-security / cb-rail, not fixed): F1 a file attached to a DISPUTE message fans out to the full chit roster, because the lookup reads only visibility_entity_id and a dispute message has visibility NULL (baseline :733-736 scopes dispute copies by dispute party instead): a participant outside the dispute holds a stored copy (it is not listed to them, the thread lists by messages they can see, and they never receive the id); F2 a message_id the caller cannot see (a counterparty's internal note, a dispute they are not in) is written into every roster copy, so it can show under that message in the other shop's own thread (needs the uuid, which is never sent to the caller); F3 a file whose name has a character above U+00FF (any Devanagari, Arabic or emoji name) uploads, then GET answers 500: Node refuses the Content-Disposition header (ERR_INVALID_CHAR, checked on this node) and the catch answers 'Fetch failed'.

(b) Conflicts with rules
- NO BEHAVIOUR CHANGE. The body schema says what the handler already takes: an object OR a list (a list was read as no fields and answered the route's own 400), nothing required (the handler's own 400 names the three it needs), every value anything. An unknown key is dropped today (`participants`, `audience`, `entity_id` are ignored: tests/rail-truth.realstack.cjs:133), so strict_input stays open on POST; closing it would turn a dropped key into a refusal. The schema check in front of POST can therefore refuse nothing; the refusal the kit declares for it is declared at 400 (the status the route answers itself).
- GET /:id's path id is plain text: a non-uuid id reaches `WHERE id = $1` and is Postgres 22P02, a 500 'Fetch failed' (not a 404). That is a behaviour question (API-4c, cb-rail), not made a 404 here. So GET answers 404 only for an id the caller's copy does not hold; error_tests stays partial on GET: the schema 422 the kit declares for an id route is never answered.
- The success of GET is bytes, declared with the kit's media() (application/octet-stream is the honest declared type; the real type is one of eight image and pdf types). The headers (Content-Type, nosniff, Content-Disposition, Cache-Control) are not touched.

(c) Simpler way: none. One router, one contractOf; `words` and `faultOf` over lib/products-contract.js `failed`/`said`, as supplies and bell do. Nothing in lib/storage.js, db.js or the libraries is edited.

(d) Risks: each refusal gains the Problem fields beside every old key (the old 400, 403, 404, 413, 500 keys and their order kept; the 401 is the auth middleware's and is not this file's). The web reads POST by status and `id`, GET by `res.ok` and 404 (public/app/attach-ui.js, app.html), and lib/autoraise.js posts to it and ignores the answer. docs/contracts/web-api.json holds no entry for either route. The 413 of a body over the 8 MB limit is the server-wide limiter's (lib/limits), not this file's, and is not touched. The relay moves into faultOf and still relays only the constant sentence; the raw-error ratchet stops counting it, and the PR says so. output_allowlist and trips_budgeted are LISTED (laptop1 ruling), never closed by hand.

(e) VERDICT: BUILD WITH CHANGES (the two relays move into faultOf; strict_input on POST, error_tests on GET, trips_budgeted on GET and output_allowlist where the generated case cannot reach a 200 are listed; three findings go to cb-security / cb-rail). No route is signed; human{} stays null.
