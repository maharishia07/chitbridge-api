# Critique · API-4 sweep: actors (20 routes of routes/actors.js) · written with the capture, before the first route edit was committed

(a) The brief assumes, checked against the code
- 20 routes, mounted at /api/actors (server.js): TRUE (the register counts 20 rows of routes/actors.js, all "not started").
- GET /check-login, POST /set-pin and POST /login are only ALIASES of routes/signin.js handlers (signin.handlers.checkLogin, signin.pinChecks + handlers.pin, signin.door('actor-login') + handlers.verify): TRUE (routes/actors.js:672, 675, 775). Their validators and refusals belong to routes/signin.js, whose own sweep is not done. Left partial, RECORDED byte for byte by the test, not edited. So 17 of 20 are swept.
- Every refusal is a bare `res.status(N).json({ error, message })` and every 5xx goes through safeErr: TRUE (about 60 sites; no `err.message` in an answer). One catch READS the message to choose an answer (GET /access-events: a table not migrated yet answers 200 `applied: false`) and relays nothing.
- The refusals of the first-code library (lib/employee-code refusal: 503 EMAIL_DELIVERY_NOT_CONFIGURED, 400 EMPLOYEE_EMAIL_REQUIRED) are `{ status, body }` pairs the routes send raw (POST /, DELETE /:id/pin, POST /:id/otp, PUT /:id/status reactivate). The library is not touched; the routes send the same pair as a Problem with every old key kept.
- Three of the 20 do several jobs on one field: PUT /:id/status (action remove / reactivate / deactivate), PUT /assign/:chit_id (pull / push / return) and PUT /:id/tasks/route (pool / push). FLAGGED, not split. Their schemas declare the action as the enum the handler already refuses an unknown value with the same 400 (status, assign); the third (tasks/route) answers an unknown action 404 for an unknown task before it answers 400, so it declares none.
- LATENT FAULT, not touched: `loginIdFor` calls `query(...)`, but in this file `query` is express-validator's `query` (line 84), not the database helper, so the read always throws, is logged as "the read failed — carried on without it", and `login_format` of PUT /:id/status (reactivate), POST /:id/otp, DELETE /:id/pin and POST /suggest-key is always the slug of the owner's display name, never the User ID the comment says it teaches. Listed for cb-people.
- tests that read this file's source (actors-max-tasks-cap, access-events, employee-code, iam-access, signin-routes ...) are checked after the edit; any that names a line is re-pointed in the same commit, never weakened. Two were: actors-max-tasks-cap (the guard line and the code's home) and scoped-access-count (the contract names all_task_visible, reads nothing).
- PUT /assign/:chit_id: the readability guard reads its 136-line transaction callback as "crossed a hard limit" once the file shrinks (it pairs untouched anonymous callbacks by nearest line), so the callback is factored into pullChit / pushChit / returnChit: the same statements in the same order (409 statements with their parameters compared against the untouched base: identical). Not a split of the route.
- FOREIGN-ID WORLD, found while building the test: PUT /:id/tasks/route never looks the person in the path up (only the chit, which is shop-scoped), and lib/assign-chit taskCount updates identities by identity_id alone, so the route answers 200 for an unknown person and can release the task count of another shop's actor by uuid. Not fixed (behaviour change); listed for cb-security as a finding.

(b) Conflicts with existing rules
- A body that is not an object (a list) is a new 400 on PUT /settings and PUT /:id/delegate (it was accepted: an empty list cleared the cover, or saved nothing), on PATCH /:id and PUT /:id/tasks/route (it was 400 in the route's own words) and a doubled `?page=` on GET /:id/tasks is a new 400. No web caller sends either (grep of public/app/*.js and app.html: every body is an object literal). POST /:id/otp, the first-code re-issue, keeps accepting any body (declared object-or-list), as before: nothing on sign-in gains a refusal.
- PUT /change-pin, POST /:id/otp, DELETE /:id/pin, POST /, PUT /:id/status (reactivate) are the sign-in side of this file: no line that issues, checks or expires a PIN, a code or the token is touched (identity-auth, employee-code, dev-otp, the lock counters, loginIdFor stay as they are). Their refusals only gain the Problem fields; each success body is unchanged.
- The Problem owns `status`, `detail`, `type`, `title`, `request_id`, `errors`, `hint`: no old body of this file used any of them, so every old key rides.
